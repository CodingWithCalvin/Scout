# Gemma thinking-off pilot

This isolated .NET runner tests the two slow fallback recordings, video-04 and video-11, from the frozen fast-workflow fixture. It uses the same saved full dialogue, 65-entry catalog, production DialogueMatcher prompts/schema and independent verification, Q4_K_M Gemma weights, b11908 Vulkan runtime, 8 GPU layers, 8 CPU threads, 32768 context and 8192 maximum output tokens. Thinking is disabled both in the managed runtime and the request. The recording deadline is 40 minutes across all model calls; the runtime is disposed between recordings, including after cancellation.

The input and manifest are checkpointed in the separate pilot.db. Completion and validation failures are kept unchanged; there are no manual episode corrections. Unknown reference labels remain unknown. The thinking-on comparison includes an incomplete response and an interrupted request, so this is not a paired accuracy benchmark.

A diagnostic HTTP handler requests streamed responses, saves progress every 15 seconds of output, retains raw completed responses and interrupted partial responses privately in the benchmark database, and reconstructs the normal response shape for the unchanged production transport/validator. This preserves the sampling settings, prompt, schema, and answer content. Diagnostic streams are never treated as successful assignments before the complete response passes normal validation. Reasoning traces are not shown in the report.

Build with `dotnet build tools/Scout.GemmaPilot -c Release`. Run the DLL with input JSON, isolated output directory, and model directory. Results are in .build/gemma-off-pilot/results/pilot.db and results.html. Application Scout databases, media and production settings are untouched. Re-running the same command reuses completed checkpoints; changed configurations require a new output directory. The full-series benchmark remains stopped.


The follow-up validation pilot writes to `.build/gemma-off-pilot/revalidated`, preserving the original results. `probe_constraints.py` runs two 256-token diagnostics against the original video-11 initial request: remove only response-schema string length limits, then remove response-format constraints. Both keep the original messages, seed, temperature, thinking mode, model and hardware settings. The probes are deliberately truncated and never episode assignments; their raw streams are stored in `constraints.db`, with a 20-minute runtime watchdog.

`--audit-saved <json>` replays saved model responses through production validation without inference or modification. The generated-prose guard covers summary, event comparisons, match reasons and rejected-alternative reasons. It checks type, emptiness, existing schema character limits, repeated characters and repeated word/phrase loops. Original dialogue, copied guide cards and episode titles are not evaluated as generated prose. Invalid responses receive at most one fresh automatic attempt using original evidence; a second failure is held with both raw attempts preserved. This catches corruption, not semantic mistakes or hallucinations. The inference cache revision changes. The saved-result format version remains compatible; resume validates accepted saved explanations before reuse, including their initial/independent successful passes. Failed retry history does not invalidate a later healthy response.


The follow-up found corruption even without constrained decoding, with the model-card sampling parameters, and with the reasoning budget disabled. The isolated CPU probe produced clean text where GPU offload corrupted the identical short prompt. The full follow-up uses optional `--cpu` to set GPU layers to zero, leaving the other settings and original input unchanged. Its manifest records the CPU setting. GPU and CPU probes use the same pinned Vulkan executable; zero GPU layers selects CPU inference. See `.build/gemma-off-pilot/diagnosis.md` and `constraints.db` for the measured diagnostics. CPU probe timing is not an episode throughput estimate.


The shared benchmark runtime allocates an ephemeral loopback port per process to avoid fixed-port reuse failures on Windows. On an infrastructure interruption, rerunning an unchanged manifest reuses finished case checkpoints and runs only unfinished cases. After completion, `python tools/Scout.GemmaPilot/render_results.py <output directory>` renders the new predictions and original evidence directly from the read-only pilot database; it never edits predictions.
