# Compact verification benchmark

This offline runner evaluates the production `DialogueMatcher` on a frozen copy of the original 13 difficult Victorious cases (12 unique dialogues). All unique dialogues receive fresh identification and compact verification. Exact duplicate dialogue reuses one result. It never opens media files or the application database, and never adjusts model predictions or reference labels.

```powershell
dotnet build tools/Scout.VerificationBenchmark -c Release
dotnet tools/Scout.VerificationBenchmark/bin/Release/net11.0-windows/Scout.VerificationBenchmark.dll .build/verification-benchmark/fixture.json .build/verification-benchmark
python tools/Scout.VerificationBenchmark/render_results.py .build/verification-benchmark
```

The personal fixture contains saved cues, the original provider catalog, inherited labels, saved Gemma outputs and recording fingerprints, and non-secret inference settings. Only cues and catalog enter inference. References, filenames, saved decisions and fingerprints are used after prediction for scoring and collection resolution. The fixture and manifest are frozen before inference. A different fixture, core assembly or configuration requires a new output directory.

SQLite may normalize recording rows into `file_results` rather than embedding them in the report's `documents.content`. The separate `recording-proofs.json` document snapshots these existing fingerprints with source provenance; it only informs grouping after inference. `--finalize` requires all case checkpoints and regenerates aggregate reports without loading a model or issuing any inference request. It never changes the saved case predictions.

The runner requires managed CPU inference, zero GPU layers and explicitly disabled thinking. The current experiment uses Gemma 4 31B Q4_K_M, eight CPU threads, context 24576, output allowance 4096 and the b11908 CPU runtime. Downloads are disabled; the installed model is checksum verified. It allocates a private ephemeral port and stops only its own server. Both passes use the unchanged original dialogue. The model receives no previous generated answer. Prompt caching is requested; actual cached tokens and prefill/generation timings are recorded rather than assumed.

The managed CPU Gemma profile enables `--swa-full`: retaining the full attention cache costs additional RAM but permits rollback to the shared dialogue prefix after the stage-specific catalog suffix. The normal rolling SWA cache can lose that state; this pinned server checkpoints user-message boundaries and the end of prompts rather than arbitrary mid-message prefix boundaries. Other model profiles, GPU-offloaded configurations and externally managed servers are unchanged. This cache policy is part of the new workflow being measured. The baseline retains the old rolling-cache configuration.

Before loading a model and before each fresh case, the benchmark waits for the existing Scout endpoint to be absent or idle for 60 seconds. It never pauses or cancels the user's Scout. An initial contention preflight was stopped before any answer completed; its artifacts are preserved separately and excluded from benchmark outcomes. The runtime-observation monitor records any later concurrent work, which must be disclosed as a timing limitation.

The compact response contains an assessment, coverage, numeric candidate IDs, verdicts, evidence indices and brief explanations. The tool resolves IDs to authoritative catalog titles/descriptions for display; it does not change the model's selected IDs. The initial plot summary is reused only when the two passes agree on assignment, assessment and coverage. Otherwise the review uses the verification explanation. Unsupported, malformed, conflicting or nonconsecutive assignments remain held. Structural validation retries are limited to one fresh response. No failed response is patched into an accepted answer.

An interrupted development attempt produced several checks for different subplots of the same episode. Both model responses were rejected and preserved in `literal-prefix-v5/benchmark.db`. The generic verifier prompt now explicitly requests one check per distinct episode candidate, and duplicate-ID validation explains that rule when requesting a fresh response. Nothing merges, deduplicates or repairs model decisions. The optional fourth argument to `prepare.py` reads a previous isolated benchmark, prioritizes its failed cases plus the preselected Playdate case, and freezes the execution order before inference. A preflight inference/validation failure stops the remaining suite; agreement with reference labels never controls continuation. All 13 cases receive the same final revision, with successful exact-dialogue reuse as usual. This is a development regression suite, not a blinded accuracy test.

Prompt-source JSON uses literal Unicode and ordinary dialogue characters rather than HTML-safe Unicode escapes inside the prompt string. It is still valid JSON inside a normally serialized HTTP payload; decoded dialogue/catalog objects are identical, including quotes, backslashes and control characters. This avoids teaching the model to read sequences such as `\u003E` instead of `>`. A tokenizer-only preflight on the longest fixture reduced the initial prompt from 24,222 to 15,069 tokens without removing evidence. The earlier cache pilot (case 01) is retained separately; the final cohort uses the updated encoding for every fresh prediction.

`benchmark.db` stores the fixture, manifest, raw requests/responses, per-request cache/timing data, case checkpoints, summary, and isolated collection report. The HTTP recorder preserves normal non-streaming production requests. A 30-minute request deadline and 70-minute case watchdog bound inference. Two consecutive case failures stop the benchmark. Restarting the same executable and arguments reuses case checkpoints. A completed benchmark refuses inference reruns.

The HTML report is derived only from saved outputs. Inherited labels are not an independent truth audit; this small, selected, single-series fixture does not establish general accuracy or multipart performance. Synthetic tests cover combined/split constraints. The historical Gemma run used thinking and GPU offload, so its elapsed time must not be presented as a controlled speed comparison. Prefix cache reuse is transient within the running server, not persisted across restarts; unrelated/interleaved requests or model-specific cache limitations can reduce hits.

For a controlled verification-stage timing check, `Baseline/Scout.VerificationBaseline.csproj` references the frozen pre-change published core (its SHA-256 is checked). After the new benchmark finishes, run it with the new benchmark directory and a separate baseline output directory. Cases **01 and 07** were selected before benchmark results: the feature/non-episode case and the earlier Playdate confusion case. The original verifier receives exactly the same cues and candidate shortlist as the new verifier, with identical CPU/model/thread/context/output/thinking settings. It starts cold, matching the old workflow's observed lack of prefix reuse. New verification uses the real preceding identification cache; no artificial cache warmup is included. Compare verification-stage time separately from full identification time. Keep both raw outcomes, including disagreements; this is not a reason to alter either prediction.

llama.cpp's pinned [server documentation](https://github.com/ggml-org/llama.cpp/blob/b11908/tools/server/README.md) documents prefix caching and the `timings.cache_n`/`usage.prompt_tokens_details.cached_tokens` measurements. Cached and uncached inference can differ numerically; all resulting predictions still undergo the same evidence and coverage validation.
